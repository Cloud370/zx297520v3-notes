# 10 元随身 Wi-Fi 折腾日记：ZX297520V3、AMT root，以及没刷成的新内核

2026-11-12

最开始的想法很直接：拿便宜的 USB 随身 Wi-Fi，刷个小系统，最好还能跑 Landscape。后来要求降了不少，能跑精简 Linux、保留 Wi-Fi、执行自己编译的程序就行。

这次是我和 Codex 一起折腾的。它负责查资料、读程序和写探测脚本，我负责设备和拔插。过程里有几次误判，也有脚本写错导致的掉线，下面都保留了，免得别人再踩一遍。

先把结果放前面：**拿到了设备 Linux 的 root，完整备份了 16 MiB NOR，还在真机跑了一个自己生成的 ARM 程序。没有刷入新内核，Wi-Fi 客户端也没连成功。** 最后停止试验，恢复了设备正常模式。

这里放的是这一次的记录，不是所有“中兴随身 Wi-Fi”都通用的刷机教程。

## 先认错机器，再认机器

一开始还在往高通 410、OpenStick 那个方向想。实际读管理页面才发现不对：

| 项目 | 这台设备的结果 |
| --- | --- |
| 管理页面平台 | `ZX297520` / `ej6A` |
| 页面固件版本 | `7520V3SCSDKV2.01.01.02P38` |
| AMT 固件版本 | `7520V3SCV2.01.01.02P38-MIFI_MIN_SV6158_DCXO` |
| Linux Hardware | `TSP ZX297520V3` |
| 内核 | `3.4.110-rt140`，`armv7l` |
| CPU part | `0xd03` |
| 闪存 | 16 MiB SPI NOR |
| Linux `MemTotal` | `24548 kB` |

所以，MSM8916 的镜像不能拿来直接刷。外壳像、卖家描述像，都没用。

当时接了不止一台设备，还用了 HUB。这也带来一个很实际的问题：拔出来以后，很容易记错哪块是哪块。USB 端口位置只适合在连接关系没变的时候辅助定位，不能当永久身份；这个批次的 USB 序列号也不适合拿来区分设备。

下面的 root、分区表和运行结果，指的都是上面这台 P38/NOR 设备。其他同外形设备没有因此获得验证。

## 9008 这条路没走成

我问过能不能直接走 9008。后来确认这是 ZX297520V3，不能把高通的下载流程套上去。

这块板上确实有 `BOOT`、`GND` 焊点，也有 `1V8`、`VBUS`、`DM`、`DP`。但当时没条件可靠地短接再上电，硬件入口就没有继续。`DM/DP` 是 USB 数据线，也不是看到焊点就随便短接。

网上有这个平台的 [USB loader 项目](https://github.com/zx297520v3-mainline/zx297520v3-loader)，用途包括从 USB 启动 U-Boot。它是重要参考，但**这次没有实测那条下载路线**，也没有用别人设备的 loader 或 NAND 镜像去写我的 NOR。

这次看到的几个 USB ID，意义也不一样：

| VID:PID | 本次观察或资料对应的用途 |
| --- | --- |
| `19d2:1225` | 启动时短暂出现的虚拟光驱/存储状态 |
| `19d2:1557` | 正常模式，有 USB 网卡和存储接口 |
| `19d2:0581` | 调试相关模式，本次 ADB 没握手成功 |
| `19d2:0201` | AMT 测试模式，本次 root 的入口 |
| `19d2:0256` | 参考下载工具中的目标 ID，本次没有进入验证 |

`0201` 不是已经进了 BootROM。看到一个新 PID，也不代表拿到了刷写权限。

## 网页里转了一圈，最后还是从网页进了 AMT

前面试过打开调试开关、导入 Telnet 配置、连接 ADB。比较典型的结果是：

- 配置能保存，重启后也能读回来，但服务端口不一定真的打开。
- Windows 能打开 ADB 对应的 USB 接口，不代表设备端会回答 ADB 握手。
- 后来在 AMT 系统里能看到 `adbd` 进程，但当时 USB gadget 只启用了 `serial,diag`，照样没有可用的 ADB 接口。

所以我现在不会再把“配置返回成功”“进程在运行”“USB 接口出现了”当成同一件事。

转机来自对同平台程序的分析：`AT+ZVERSIONTYPE=1` 在这个固件流程里会设置测试启动标记。对这台设备发送后，确实返回了 `OK`；再重启，USB 变成了 `19d2:0201`。

下面是当时使用的网页请求形式。**先登录自己的设备管理页，并确认平台和版本。不要在接着多台同地址设备、目标没分清的情况下直接执行。**

在已登录管理页的浏览器控制台中：

```javascript
const result = await fetch('/reqproc/proc_post', {
  method: 'POST',
  body: new URLSearchParams({
    isTest: 'false',
    goformId: 'ID_SENDAT',
    at_str_data: 'AT+ZVERSIONTYPE=1'
  })
}).then(r => r.json());
console.log(result); // 本机实测 { result: "OK" }
```

只有确认前一步返回 `OK`，才执行重启请求：

```javascript
await fetch('/reqproc/proc_post', {
  method: 'POST',
  body: new URLSearchParams({
    isTest: 'false',
    goformId: 'REBOOT_DEVICE'
  })
});
```

重启时连接被关闭是可能的，不能只凭这个异常判断成功。下一步要在设备管理器里检查实际枚举结果。

这一步会让网页暂时不可用。它也依赖原厂接口没有被删掉、改名或关闭；本仓库的小工具**不负责进入 AMT**，不要把工具已经准备好理解成一定能恢复任何固件。先准备好匹配的串口驱动和恢复思路；如果启动标记仍是 AMT，单纯反复拔插并不会自动改回正常模式。

## 真正拿到 root：原来它等的不是 AT 文本

进入 `0201` 后，一开始没有可用的串口驱动。后来从同平台的 ZTE 开发驱动里找到了匹配项：

- `MI_00`：`AT Interface`
- `MI_02`：日志接口

本次只安装了匹配的签名 INF，检查过目录签名和驱动签名。没有关闭 Windows 驱动签名检查，也没有运行来路不明的“一键解锁”程序。驱动包不放进仓库；可查阅 [ZLT_S10_CPE 的驱动资料目录](https://github.com/thiwaK/ZLT_S10_CPE/tree/main/assets/bins/drivers)，但那是别的设备项目，不能把整套刷机流程搬过来。

设备管理器里显示“AT Interface”挺容易误导人。我最初往里面发普通 `AT`，它不回；后来才从参考 `zte_amt` 程序里确认，这个模式下接收的是二进制帧。

当时用于读协议的是 [X2 参考固件仓库](https://gitlab.com/ZX7520v3_Firmwares/xinxun-mifi/X2)中 `X2_CN_XX_TH_P42U05_W_08_20230911` 分支的 `files/bin/zte_amt`。它是另一版固件，不是本机 P38 的备份；协议是否匹配，最终仍靠下面的真机应答确认。这里只链接来源，不转发其中的二进制。

格式很小：

```text
4 字节小端长度 N
02 | 2 字节大端命令号 | 参数 | XOR 校验 | 02
```

`N` 是后面整帧的长度，不包括最前面的 4 字节。校验是命令号字节与参数字节逐个异或。

第一条真正收到有效回应的是平台查询：

```text
发送：05 00 00 00  02 10 04 14 02
收到：06 00 00 00  02 10 04 01 15 02
```

长度、命令号和校验都对上了，返回数据是 `01`。这比“串口能打开”有说服力多了。

接着用 `0x00d1` 读到了上面的 P38 内部版本。真正的关键是 `0x00c1`：参考程序把这类 Wi-Fi 测试命令的参数交给了 `popen(..., "rb")`，再把标准输出返回。

于是只发了一条 `id`：

```text
发送：07 00 00 00  02 00 c1 69 64 cc 02
参数：id

返回的文本：uid=0(admin) gid=0
```

到这里才算确认拿到了 root。不是根据页面上的“调试已开启”猜的，也不是拿参考固件的反编译结果当真机结果。

### 这是主系统吗？

准确说，是设备应用处理器上的 Linux，当前以 `bootmode=amt` 启动，挂载了本机 `rootfs` 分区。后面从这台自己的备份里提取 `/etc/rc`，看到正常模式和 AMT 共用这份启动脚本：AMT 分支启动 `zte_amt`、`adbd` 后提前退出，后面的正常联网服务不会按正常分支继续启动。

所以它不是 Windows 的权限，也不是 BootROM 提示符。但我也没有因此宣称“正常联网模式下的常驻 root 已做好”。这两件事还差着启动流程和访问通道。

## 两个真的把我坑住的协议细节

### 输入只有 255 字节可用

参考程序给命令字符串分配了 256 字节，再复制参数并补一个 NUL。可用命令长度最多是 **255 字节，按字节算，不是按字符算**。

这不是事后补的一句提醒。我让脚本把测试 ELF 转成一长串八进制 `printf` 命令，长度到了 636 字节，发送后设备掉线了。复查才发现漏了这个上限。它可能破坏了进程堆内存，不能算普通的“命令执行失败”。

后来加了长度和内嵌 NUL 检查，改成每次上传 32 字节，才跑通。附带工具已经带上这个限制，不接受任意 shell 命令。

### 输出也不是终端

返回缓冲区约 2 KiB，其中最后一个字节还会被覆盖成 NUL。读闪存不能直接一次取 2048 字节，所以实际采用了每块 1024 字节。

无输出的命令也可能没有响应。更麻烦的是启动后台程序：如果子进程仍拿着输出管道，接收端可能一直等，整个命令通道就卡住了。`-B` 返回到后台，不自动等于这个管道已经关闭。

后面测试 Wi-Fi 时，把子进程的 stdin、stdout、stderr 都处理清楚，才得以稳定读日志。正常串口会话不是交互式 shell，不能按 SSH 的习惯使用。

一旦收到半帧、超时或校验错误，我采用的是停止本轮请求，而不是继续往同一条流里灌命令。最开始把普通 AT 文本送进二进制入口，也可能让长度解析跑偏；当时确实需要断电重插才能继续。

另外，几次掉线曾让我怀疑是关闭串口触发了关机，但后来有立即关闭再重开成功的记录。**这个猜测没有被证实**，不能把所有掉线都归到它身上。

## 有 root 后，先把闪存读出来

实机 `/proc/mtd` 的布局是：

| 分区 | 名称 | 大小 | 起始偏移 |
| --- | --- | ---: | ---: |
| mtd0 | zloader | 64 KiB | `0x000000` |
| mtd1 | nvrofs | 512 KiB | `0x010000` |
| mtd2 | uboot | 256 KiB | `0x090000` |
| mtd3 | imagefs | 4480 KiB | `0x0d0000` |
| mtd4 | rootfs | 9600 KiB | `0x530000` |
| mtd5 | userdata | 1472 KiB | `0xe90000` |

总共 `0x1000000`，也就是 16 MiB。擦除块是 64 KiB。

这跟不少参考资料里的 128 MiB NAND 完全不同。到了这一步，更不可能直接套别人分区表了。

读取形式是：

```sh
dd if=/dev/mtd0ro bs=1024 skip=0 count=1 2>/dev/null
```

脚本逐块读取六个只读 MTD 节点，保存文件和 SHA-256。全部读完以后，再从设备读第二遍，逐字节比较。最终六个分区都一致；本地又重新计算了一遍文件哈希和长度。

这份备份是**当时状态的备份**，不是出厂未修改镜像。前面已经改过配置和启动标记，不能因为文件名叫 backup，就把它描述成“原厂救砖包”。两遍一致也只是读出一致，不等于已经验证能刷回去启动。

备份里可能有设备身份、网络配置、校准数据，原始文件不公开。

## 只有 24 MB 内存？我也问了这个问题

读到 `MemTotal: 24548 kB` 时，第一反应也是怎么这么小。

继续查 `/proc/iomem` 和 memblock，Linux 的 System RAM 范围是：

```text
0x20440000 .. 0x21ffffff
```

这个范围是 27.75 MiB，其中还有内核代码、数据及保留区域。`MemTotal`、这个地址范围、整机物理 RAM，是三个不同口径。

[中兴微官方规格](https://www.sanechips.com.cn/chinese/product/shoujichanpin/shoujimodemxinpian/1556481512885469186.html)列了 256 Mb、512 Mb、1 Gb LPDDR2，换成字节容量是 32、64、128 MiB。特别注意这里的 `Mb`，不是 `MB`。[Linux 平台文档](https://kernel.googlesource.com/pub/scm/linux/kernel/git/pcmoore/audit/+/HEAD/Documentation/arch/arm/zte/zx297520v3.rst)也提到有 32 MiB RAM、8/16 MiB NOR 的设备，以及内存与 LTE 部分共享的情况。

这让“它可能是 32 MiB 版本”说得通，但本次没有拿到足够证据把物理总容量彻底定死。16 MiB 闪存则是另外一件已经实测确认的事。

## 自己的程序，确实跑起来了

原厂程序是 ELF32 ARM EABI，动态解释器是 `/lib/ld-uClibc.so.0`。不能随便拿一个 x86 程序或者 ARM64 程序塞进去。

为避开 libc 和浮点 ABI，测试用了一个只调用 `write`、`exit` 的静态 ARM ELF。总大小 139 字节，不依赖编译器生成物；附带 Python 工具直接生成同样的 ELF。按 32 字节拆开上传到 `/tmp` 后，真机返回：

```text
ARM binary executed OK
RC:0
```

这个结果至少证明：能传文件，能执行自己构造的本地程序，能拿回输出。

它不证明任意 Rust/Go 程序都能直接跑，也不证明现代 glibc、硬浮点或 ARM64 可用。至于 Landscape，原本想跑的那套软件还涉及新内核、BPF、架构和内存要求，这次没有继续硬上。

## Wi-Fi：有硬件，有驱动，但这次没有连成

本机备份里找到了：

```text
ssv6xxx_prealloc_skb.ko
ssv6x5x.ko
ssv6x5x-wifi.cfg
hostapd
wpa_supplicant
```

SDIO 实机 ID 是 `5653:2060`，和模块的 alias 匹配；模块 vermagic 也与当前 `3.4.110-rt140` 匹配。固件名称和驱动内嵌字符串进一步指向 SV6158 系列。原厂模块加载后，出现了 `wlan0`、`wlan0-vxd`。

本机页面配置是 `WIFI_HAS_5G=false`。扫描能看到家里 2.4 GHz 的热点，看不到单独命名的 5 GHz 热点。这台的 5 GHz Wi-Fi 就没有继续指望了；这里说的是 Wi-Fi 频段，不是移动网络 5G。

连接先走的原厂网页接口，基本顺序如下：

1. `WIFI_STA_CONTROL` 开启客户端。
2. `WLAN_SET_STA_REFRESH` 触发扫描。
3. 读取 `scan_finish`、`EX_APLIST`、`EX_APLIST1`。
4. `WIFI_SPOT_PROFILE_UPDATE` 保存连接配置。
5. `WLAN_SET_STA_CON` 使用相同 profile 发起连接。

只发连接请求、不先创建 profile，我这里返回过失败。照着本机 `ap_station.js` 和 `service.js` 补齐以后，接口返回成功了，但 `sta_ip_status` 仍然是 `disconnect`，没有拿到 IP。

所以又回到 root 通道查它原来怎么连。原厂 `zte_mifi` 启动的也是自己的 `wpa_supplicant`，使用 `nl80211`，读取 `/etc_rw/wifi/wpa_supplicant.conf`。并没有什么必须另找的神秘拨号程序。

其中还踩了一次裁剪版工具的坑：这个 `wpa_supplicant` 不支持 `-f` 日志参数，给了参数以后输出帮助，甚至不能只看退出码判断已经启动。改成 shell 重定向，再按前面说的方式处理后台进程管道，才拿到实际日志。

用原厂虚拟接口和主接口分别测试，都是类似的过程：

```text
SCANNING -> AUTHENTICATING
SME: Authentication timed out
AUTHENTICATING -> DISCONNECTED
```

这是无线认证阶段超时，尚未完成后面的 WPA 密钥握手，更没到 DHCP。保存的密码已经核对过，不能看到“认证”两个字就直接说密码错了。

设备自己的扫描结果里，家里热点的信号大约是 `-86` 到 `-88 dBm`，而手机连同一个 Wi-Fi 是满格。因此我最后怀疑的是这块设备的接收、天线、射频或驱动状态，但没继续拆，也没有定位出具体故障。**天线坏了只是猜测，没有实锤。**

有 [SSV6x5x 相关开源驱动](https://github.com/OpenIPC/ssv6x5x)可以继续研究，但找到相近名字的源码，不等于已经适配了这台板，也不等于旧 `.ko` 能直接装到新内核。

## 最不应该踩的一个坑：名字像查询，也可能写东西

前期曾在另一块设备上把 `AT+WSCYINFO` 当成信息查询。实际返回了 `+write security infomation`。随后分析参考程序，发现相关处理可能涉及安全标志和 eFuse 写入。

操作前没有快照，没法确认那块设备究竟有没有被改变。后续也没有再重试这条命令。

这是这次最不该犯的错。不要把命令名里有 INFO、状态、查询之类的字样当成只读保证，更不要靠不断试“隐藏 AT 命令”来碰运气。本仓库工具没有这个命令，也没有通用 AT 执行入口。

## 最后怎么收的尾

停止自建的无线测试进程，用已经验证过的 AMT 命令恢复下一次正常启动标记：

```text
命令：0x1000
参数：00
响应数据：00 00 00 00
```

这是**写启动标记**，不是只读查询。返回成功也不等于当前已经切回正常模式，需要重新启动并检查。

随后实测恢复了正常 USB 网卡和 P38 管理页面，关闭了这轮开启的 STA，删除了测试 profile，确认原厂热点仍开启。没有继续刷内核，也没有为了追求一个“刷机成功”的结尾而写入不匹配的镜像。

## 仓库里留下什么

只有这篇记录、一个小工具、它的离线测试和许可证。`amt.py` 从当时的脚本精简而来，保留：

- `probe`：版本、`id`、内存及 MTD 查询。
- `backup`：限定这张分区表，读取两遍并校验。
- `hello`：固定 139 字节程序，分块上传、读回比较，再运行和清理。
- `recover`：显式写入下一次正常启动标记，不自动重启。

**公开版 CLI 做过离线协议和模拟设备测试，没有为了发仓库再打扰已经收尾的设备。** 真机验证的是前面描述的原始交互和算法，不要把两种验证混为一谈。Windows 签名串口驱动与已进入 AMT 是使用前提；其他操作系统和其他固件不在本次验证范围。

安装依赖后，手动选设备管理器里的 **AT Interface** 端口，不能选日志口：

```powershell
python -m pip install pyserial==3.5
python amt.py --port COM9 probe
python amt.py --port COM9 backup ./private-backup
python amt.py --port COM9 hello
python amt.py --port COM9 recover
```
